# Interrogate the ask before accepting the interface

## In brief

An ask arrives at some altitude. It might prescribe the interface—"design a chat interface for this bot"—or it might be as broad as "add AI to my product." Either way, step back before designing. A prescribed interface might ultimately be the right approach, but treat it as one candidate, not the requirement. A broad mandate gives you leeway, but demands the same question: what is the actual value being added?

## From ask to value to capabilities to interface

Work the chain in order:

1. **What is the value?** "We want a chat interface" → why? What is it for? "Add AI" → what value does the AI actually provide to the people using this product?
2. **What are the capabilities?** Capabilities are the things a user wants done by the system that it can now do. The value names them.
3. **What interface surfaces them best?** Only now choose. Sometimes the answer is the prescribed interface—conversational interaction alongside deterministic buttons may genuinely want a chat surface. Then the questions continue at lower altitude: traditional message bubbles, or a turn-by-turn treatment that is less obviously a chat?

The chain is the altitude principle applied to a brief: examine it from above before building it from below.

## Working rules

- Treat a prescribed interface as one candidate approach, not the requirement.
- Ask what value the feature provides before asking what it looks like.
- Name the capabilities—what users want done by the system—before choosing the surface.
- Keep asking the same questions at each lower altitude once the surface is chosen.
